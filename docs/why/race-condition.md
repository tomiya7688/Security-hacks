# 在庫は1個なのに、なぜ2人に売れてしまうの？

> **「『在庫があることを確認してから販売』と書いたのに、なぜ注文が重なってしまうの？」**

## 確認した瞬間と、実際に動かす瞬間は別

最後の1個の商品を、AさんとBさんがほぼ同時に注文する場面を考えます。

```text
在庫：1個

Aさん：在庫を確認 → 1個ある！ ─────────→ 1個減らす
Bさん：        在庫を確認 → 1個ある！ → 1個減らす

結果：注文は2件、在庫は -1個？
```

どちらも「在庫があるか確認した」こと自体は正しいのに、**2人とも古い情報をもとに処理を進めてしまっています**。

複数の処理が同じ情報を使うとき、動く順序によって結果が変わってしまう問題を**競合状態（レースコンディション）**といいます。

特に、**確認してから使うまでの間に状態が変わる**種類の問題を、英語の頭文字で**TOCTOU（トクトウ）**と呼びます。

## やってみよう：順番を決めて再現する

これはPython 3だけで動き、ネットワークや大量の同時アクセスを使いません。あえてAさんとBさんの「確認」を先に終わらせることで、**同時処理で起こる失敗を再現**します。

```python
stock = 1

a_saw_available = stock > 0
b_saw_available = stock > 0  # Aの更新前の在庫を見ている

if a_saw_available:
    stock -= 1
if b_saw_available:
    stock -= 1

print("古い確認結果を使った在庫:", stock)
```

結果：

```text
古い確認結果を使った在庫: -1
```

**確認と更新を別々の処理にしたこと**が問題です。

## では、どう直す？ 「残っているなら減らす」をひとまとめにする

データベースには、**条件の確認と値の変更をひとつの操作として扱える仕組み**があります。

次はPython標準のSQLiteで動く小さな例です。外部のサーバーは使わず、メモリ上の在庫を使います。

```python
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE stock (id INTEGER PRIMARY KEY, qty INTEGER NOT NULL CHECK(qty >= 0))")
db.execute("INSERT INTO stock VALUES (1, 1)")

def buy():
    result = db.execute(
        "UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0",
        (1,),
    )
    db.commit()
    return result.rowcount == 1

print("Aさんの注文:", buy())
print("Bさんの注文:", buy())
print("残り在庫:", db.execute("SELECT qty FROM stock WHERE id = 1").fetchone()[0])
```

結果：

```text
Aさんの注文: True
Bさんの注文: False
残り在庫: 0
```

`UPDATE` はデータの更新を頼む命令です。ここでは「在庫がまだあるなら1個減らす」という**条件付きの更新**を1回で行います。`rowcount` を見れば、更新に成功したか判断できます。

このように、途中に別の操作が割り込んで中途半端な状態が見えないよう、一体として扱う処理を**原子的（アトミック）な処理**といいます。

## どう防ぐ？

- **同じデータの確認と更新を、できるだけひとつの安全な操作にする。**
- それが難しい場合は、データベースの**トランザクション**や適切な**ロック**で、途中に別の処理が入り込まないようにします。
- 在庫が負にならない、同じ注文を二重処理しないといった**データ側のルール**も用意します。
- 同時実行のテストは「順序が変わっても正しいか」を確かめます。

## ここまでは分からない

上のSQLite例は、**同じデータベースに順番に2回更新を送る**だけの学習用コードです。何千件もの注文や複数サーバー間の競合を、そのまま解決する完成品ではありません。

実際のサービスでは、注文確定と決済が別システムだったり、通信失敗で要求が再送されたりします。**データベースの更新が安全でも、決済や通知の二重実行まで自動で防げるわけではありません。**

また、[返却済みのメモリを使ってしまう問題](memory-safety.md)も、同時処理のタイミングから生まれる場合があります。
