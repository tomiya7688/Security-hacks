# 別のサイトを見ただけで、なぜログイン中の設定が変わることがあるの？

> **「自分は設定変更ボタンを押していないのに、なぜ操作したことになってしまうの？」**

## ブラウザーは「ログインを覚える情報」を自動で送る

サイトにログインすると、ブラウザーは「この人はログイン済み」と確認できる情報を預かることがあります。これを**Cookie（クッキー）**といいます。

問題は、Cookieが**利用者の意思とは関係なく、条件に応じてブラウザーから自動で送られる**点です。

例えば、あなたがAというサービスにログインしたまま、Bという別のサイトを開いたとします。B側がAに向けた操作要求をブラウザーに出させることがあります。条件がそろうと、AはCookieを見て「ログイン中の人から来た」と判断してしまうかもしれません。

```text
あなた ──ログイン──→ サービスA
   │
   └── 別サイトBを見る
            │
            └── Aへの「設定変更」要求をブラウザーに出させる
                         │
                 AがCookieだけで判断すると…
                         ↓
                あなたの操作だと誤認する場合がある
```

**本人の意思で送ったとは限らない操作を、ログイン中の利用者の操作として受け付けてしまう問題。これをCSRF（クロスサイトリクエストフォージェリ）といいます。**

## ログインの確認だけでは足りない？

ログイン確認が分かるのは、基本的に**誰のログイン状態か**です。「この操作を本当にこの人がサイトAで始めたか」は、それだけでは判断できません。

なお、**Cookieが別サイト経由の要求に必ず付くわけではありません。** ブラウザーの制限やCookieの設定、要求の種類によって変わります。しかし、設定や設計の条件が合えばCSRFは起こり得ます。

## やってみよう：要求に「本人が画面で受け取った目印」があるか

次は、Web通信をしない**考え方の模型**です。Python 3だけで動きます。

```python
import hmac
import secrets

# 本物のサービスならサーバーが利用者のログイン状態と結びつけて保管する
session_token = secrets.token_urlsafe(24)

def accept_change(logged_in, submitted_token):
    if not logged_in or not isinstance(submitted_token, str):
        return False
    return hmac.compare_digest(session_token, submitted_token)

print("目印なし:", accept_change(True, None))
print("正しい目印あり:", accept_change(True, session_token))
```

```text
目印なし: False
正しい目印あり: True
```

サーバーだけが検証できる**予測しにくい目印**を、正規のフォームなどを経由した要求に含めて、サーバー側で確かめます。この目印を**CSRFトークン**と呼びます。上の例は目印の比較部分だけを見せています。実際にはログイン状態との結び付け、配布場所、有効期間なども必要です。

## どう防ぐ？

- **重要な更新・送信操作にはCSRF対策を組み込む。** 利用するWebフレームワークのCSRF保護機能を優先します。
- Cookieの `SameSite` を適切に設定します。ただし、**SameSiteだけですべて防げるわけではありません**。
- サーバーに記録や変更を起こす処理を、リンクを開くだけの **GET** 要求に置かないようにします。
- 必要に応じて、要求がどのサイトから来たかを表す `Origin` なども確認します。
- CSRFトークンをURLに含めたり、アクセスログに不用意に記録したりしません。

## ここまでは分からない

この模型は「ログイン済み」と「正規の操作を示す目印」の違いを説明するものです。**この十数行をそのまま実サービスに貼っても完成したCSRF対策にはなりません。**

また、ブラウザーは通常、別サイトからAの情報を**読む**ことも制限しますが、**読むことを防ぐルールと、要求を送ることを防ぐルールは別**です。CORSの設定だけをCSRF対策だと思わないでください。
