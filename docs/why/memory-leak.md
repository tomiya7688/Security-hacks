# 使い終わったメモリが戻らないのはなぜ？ — メモリリークの仕組み

> **「アプリを使えば使うほど、メモリ使用量が増える。再起動すると戻るけど、これって何？」**

## まず、メモリはどう使われる？

プログラムは、処理の途中で数字や文字列などを置くための場所を使います。机の上に「作業用の箱」を借りるようなものです。

- **箱を借りる**：作業に必要な大きさのメモリを確保する。
- **箱を使う**：データを一時的に置いて計算する。
- **箱を返す**：使い終わったら、その場所をまた使えるようにする。

例えば、毎回1つ箱を借りて、処理の終了時に返していれば、次の処理でも同じ場所を使えるかもしれません。

ところが、**箱を返し忘れたまま同じ処理を繰り返す**と、利用できる場所が減っていきます。

```text
正常な処理
1回目: [借りる] → [使う] → [返す]
2回目: [借りる] → [使う] → [返す]
3回目: [借りる] → [使う] → [返す]

返し忘れた処理
1回目: [借りる] → [使う] → [返し忘れ]  残り 1箱
2回目: [借りる] → [使う] → [返し忘れ]  残り 2箱
3回目: [借りる] → [使う] → [返し忘れ]  残り 3箱
```

*「残り」は返されずに残っている箱の個数で、実際のメモリ量を正確に表す図ではありません。*

**不要になったメモリを適切に解放できず、使用可能なメモリが減っていくことを「メモリリーク」といいます。**

## なぜ返し忘れるの？

単なる「片づけ忘れ」だけでなく、**途中でエラーが起きたとき**に起こりがちです。

例えば、普段は「確保 → 処理 → 解放」の順で動くけれど、エラー時だけ「確保 → エラー → 即終了」となるケースです。

次の短いC言語の例を見てください。危険なネットワーク操作はありません。わざと5回だけメモリを返し忘れる**ローカル実験用のコード**です。

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static int handle_request(int failed) {
    char *work = malloc(1024);   // 1024バイト借りる
    if (work == NULL) return -1;
    memset(work, 'A', 1024);    // 借りた場所を使う

    if (failed) {
        return -1;              // ここで返し忘れ！
    }

    free(work);                 // 普段は返している
    return 0;
}

int main(void) {
    for (int i = 0; i < 5; ++i) {
        (void)handle_request(1); // エラーの経路を5回通す
    }
    puts("5回処理しました");
    return 0;
}
```

- `malloc` は作業用のメモリを借りる処理です。
- `free` は借りたメモリを返す処理です。
- `return` はそこで処理を終える命令です。

上の例では、エラーが起きると `free(work)` を通らずに関数が終わります。**借りた場所の住所も見失うので、そのメモリはプログラムが動いている間、再利用できません。**

この例では **1024バイト × 5回 = 5120バイト** が解放されません。プログラム自体はすぐ終わるため、通常はOSが終了したプロセスのメモリを回収します。しかし、Webサーバーのように**長く動き続けるプログラム**で同じことが何度も起きると、困ったことになります。

## 実際に確かめる（任意）

Cコンパイラ `clang` と、そのメモリ検査機能が使えるLinuxなどの環境なら、上のコードを `leak.c` として保存して、次を実行できます。

```sh
clang -g -O0 -fsanitize=address leak.c -o leak
ASAN_OPTIONS=detect_leaks=1 ./leak
```

対応環境では、プログラムの終了時に `LeakSanitizer: detected memory leaks` といった報告が表示され、**5120バイトが5回の確保で残った**ことを確認できます。リークが見つかるため終了コードが0以外になることがあります。環境によっては検査機能が使えないため、同じ表示にならない場合もあります。

実行するのは**自分の開発環境だけ**にしてください。これは学習用のわざと間違えたコードで、本番サービスへ組み込むものではありません。

## どう直す？

この例では、エラー時に戻る前にも `free(work)` を呼べばよいです。

```c
if (failed) {
    free(work);   // 戻る前に返す
    return -1;
}
```

ただし現実のプログラムでは、エラーの経路が多かったり、別の場所がメモリを使っていたりするため、単純にどこでも `free` すればよいわけではありません。**まだ使用中のメモリを返してしまうと、別の問題が生まれます。**

大事なのは「**誰が借りて、誰が返す責任を持つのか**」を決めることです。

C++なら、使い終わると自動的に後片づけできる仕組み（RAIIやスマートポインタ）を利用する方法があります。

## Pythonならメモリリークは起きない？

Pythonには使われなくなったデータを自動で片づける仕組みがあります。それでも、**もう不要なデータをリストに入れたまま残す**と、メモリの使用量が増えます。

次の実験は最大約5MiBのデータしか作りません。

```python
import tracemalloc

tracemalloc.start()
kept = []

for n in range(1, 6):
    kept.append(bytearray(1024 * 1024))
    current, _ = tracemalloc.get_traced_memory()
    print(f"{n}回目: {current / 1024 / 1024:.1f} MiB")

kept.clear()  # もう使わないデータへの参照をなくす
current, _ = tracemalloc.get_traced_memory()
print(f"参照を外したあと: {current / 1024 / 1024:.1f} MiB")
```

ここで `kept` に入ったデータは、Pythonから見ると**まだ使われているデータ**です。そのため消えません。必要がなくなって `clear()` すると、Pythonが追跡する確保済みメモリが減ります。

これは**参照を残し続けた場合の増え方を示す例**です。C言語の「住所を完全に見失ったメモリリーク」とは仕組みが違います。また、Pythonの追跡値が下がっても、OSから見たプロセスのメモリ使用量が同じだけ下がるとは限りません。

## どうしてセキュリティの話になるの？

メモリを返し忘れるだけで、ただちに他人がプログラムを乗っ取れるとは限りません。

しかし、外部から同じ処理を何度も起こせる場合、サーバーのメモリを使い切らせて**正常な利用者がサービスを使えない状態**にできる可能性があります。これを**サービス妨害（DoS）**といいます。

**ただの性能問題になるか、攻撃に使える問題になるかは、誰がその処理をどれだけ繰り返せるかなどの条件で変わります。**

## この記事で分かったこと・分からないこと

- **分かったこと**：返し忘れると、処理が終わっても借りたメモリが残る。エラー経路が見落とされやすい。
- **分かったこと**：繰り返し起こせると、メモリ不足による停止に結びつく場合がある。
- **分からないこと**：アプリのメモリ使用量が増えたという事実だけでは、メモリリークとは断定できない。キャッシュなど、意図的なメモリ利用もある。

「どうしてメモリのミスで**勝手にコードを動かされる**ことがあるの？」については、[メモリの安全性についての記事](memory-safety.md)で別に説明します。
