# メモリの扱いを間違えると、なぜ乗っ取られることがあるの？

> **「画像を開いただけ」「文字列を読んだだけ」で、なぜプログラムが勝手に動くことがあるの？**

コンピューターは、受け取った文字列や画像をメモリという作業場所に置いて処理します。そこで「**使ってよい場所**」や「**使ってよい期間**」の約束を破ると、違うデータを読んだり壊したりすることがあります。

まずはこの2つのパターンを見てみましょう。

## 1. 用意した箱をはみ出して書く

例えば、4文字までしか入らない箱があったとします。

```text
書いてよい場所
       0   1   2   3
     +---+---+---+---+  +----------------+
     | A | B | C | D |  | 別のデータの場所 |
     +---+---+---+---+  +----------------+
                       ↑
            ここから先は自分の箱ではない
```

プログラムが「5文字でも入る」と勘違いして、5つ目まで書き込もうとするとどうなるでしょう。

**C/C++など、境界を自動で確認してくれない操作では、別のデータが置かれた場所まで書き換えてしまう場合があります。** これを**範囲外への書き込み（Out-of-bounds Write）**といいます。後ろにはみ出す形の問題は、広く**バッファオーバーフロー**と呼ばれることもあります。

普通なら書き換えられない設定や処理に関係する情報が壊れると、プログラムが落ちたり、意図しない動きにつながったりします。条件がそろうと、攻撃者がそれを悪用することもあります。

一方で、**範囲外への書き込みがあれば必ず乗っ取られる、という意味ではありません。** その場所に何があるか、安全装置が働くか、といった条件で結果は異なります。

## 2. 返した箱を、まだ使えると思い込む

もう1つ、時間の約束も重要です。

```text
① プログラムAがメモリを借りる
      A → [作業用の箱]

② Aが箱を返す
      A → [返却済みの箱]
           （Aはもう使ってはいけない）

③ プログラムの別の処理Bが同じ場所を借りる
      B → [Bのデータ]
      A → [古い場所を覚えたまま]

④ Aが昔の場所を使おうとする
      A → [Bのデータを壊すかもしれない]
```

**返した後のメモリを再び使ってしまうことを、Use-After-Free（ユース・アフター・フリー、略してUAF）といいます。**

古い場所に別のデータが入った状態で書き込めば、本来Aが触ってはいけないBのデータを壊す可能性があります。読み取りなら、別の情報を見てしまう可能性もあります。

こうした問題は、単なるクラッシュにとどまらず、**条件によってはプログラムの動きそのものを変えられる**ことがあります。

## 実際に安全な仕組みを試してみよう

Pythonには、「決められた範囲を越えて書こうとしたら、書かずにエラーで止める」仕組みがあります。

```python
boxes = bytearray(4)  # 4個の箱を用意する

try:
    boxes[4] = 65      # 5個目に書こうとしてみる
except IndexError:
    print("範囲外なので書き込めません")
```

結果：

```text
範囲外なので書き込めません
```

箱に振られた番号は `0` から `3` まで。だから `4` 番は範囲外です。

**危険な操作をしようとしたとき、実行前に止められる**。これが安全性を高める仕組みの一例です。

ただし、「Pythonならすべて安全」という意味ではありません。Pythonから使うC/C++製ライブラリなどの内部に問題がある可能性もあります。

## 「脆弱性の約70%」は何の話？

Chromiumプロジェクトは、2015年以降のChrome安定版に関する**高・重大度の問題912件**を対象に分析し、約70%がメモリの安全性に関する問題で、その約半数がUAFだったと説明しています。

ここでいう主な問題は、**メモリの使える場所や期間を守らないこと**です。使い終わったメモリを返さない**メモリリーク**の話と取り違えないようにしましょう。

そして、この数字は**Chromiumの対象期間・対象分類での集計**です。世界中のあらゆるソフトウェアの脆弱性の70%と読み替えることはできません。

## なぜこんなミスが生まれる？

プログラムは、外から来るデータを処理するとき、長さ・場所・順番・途中の失敗を考える必要があります。

- **長さの確認を忘れた**：データが用意した領域に収まらなかった。
- **解放の順番を間違えた**：使い終わったと思って返したが、別の処理はまだ使用中だった。
- **同時に処理した**：一方が返したメモリを、もう一方が触ってしまった。
- **例外的な入力やエラー**：普段の動作確認では通らない手順で、前提が崩れた。

特にC/C++など、低いレベルのメモリ操作を自分で管理できる言語では、プログラマがこうした約束を守る責任を多く持ちます。

一方、言語やライブラリの機能で範囲や使える期間を確認することは、**問題を起きにくくする方法**です。例えばRustのように、メモリの扱いに強い制約を設ける言語もあります。

## 結局、どう防ぐ？

1. **箱の大きさを確認する**：入力や配列の長さを、実際に用意した領域と比べる。
2. **誰がメモリを返すか決める**：同じ場所を複数の処理が勝手に解放しないようにする。
3. **自動でチェックできる仕組みを使う**：言語、ライブラリ、コンパイラの安全機能を活用する。
4. **普段と違う入力や順番でも試す**：テストやメモリ検査ツールを利用する。

**検査ツールを1回通せば、すべての脆弱性が消えるわけではありません。** 問題のある処理をテストで通らなければ、発見できないこともあります。

なお、メモリが増え続けるという**別の現象**については、[メモリリークの記事](memory-leak.md)で説明しています。
