# ファイル名を指定しただけで、なぜ秘密のファイルが読まれるの？

> **「資料のダウンロード機能なのに、指定されたファイル名をそのまま使うのは危ないの？」**

## ファイル名には「別の場所へ移動する」という意味もある

例えば、サービスが「公開用フォルダー」の中に置いた資料だけを読ませるとします。

```text
service/
├── public/
│   ├── guide.txt
│   └── notes/
│       └── today.txt
└── private.txt      ← 公開してはいけない
```

ここで、利用者に「どのファイルを読むか」を自由に指定させているとします。

```text
public/notes/today.txt
```

これは公開用フォルダーの中なので、想定した使い方です。

では、次の指定はどうでしょう。

```text
public/../private.txt
```

`..` は多くの環境で**ひとつ上のフォルダー**を表します。つまり「publicの中のファイル」を指定したつもりが、**外側のprivate.txtを指してしまいます**。

**使ってよいフォルダーの外へ、ファイルの場所の指定を使って抜け出す問題。これを「パストラバーサル（Path Traversal）」といいます。**

## どうして起きる？

原因は、**利用者が渡した文字列を、ファイルの場所として信じてしまうこと**です。

```python
# 危険な考え方の例（説明用）
path = public_directory / user_supplied_name
# このまま開くと、上のフォルダーへ抜ける場合がある
```

注意が必要なのは `..` だけではありません。絶対パス、特殊な表現、リンク、複数回の文字の変換などで、意図しない場所を指す場合があります。

## やってみよう：読む前に「公開用フォルダーの内側か」確認

Python 3.9以降の実験です。**自分の一時フォルダーを作り、パスの判定だけをします。実際のファイルは読みません。**

```python
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as temp:
    public = (Path(temp) / "public").resolve()
    public.mkdir()

    for name in ("notes/today.txt", "../private.txt"):
        target = (public / name).resolve()
        allowed = target.is_relative_to(public)
        print(f"{name}: {'公開範囲内' if allowed else '公開範囲外'}")
```

結果は次のとおりです。

```text
notes/today.txt: 公開範囲内
../private.txt: 公開範囲外
```

`resolve()` はパスの `..` などを整理して、実際に指す場所を求めます。`is_relative_to()` は、整理したパスが公開用フォルダーの中に収まるかを確かめます。

## どう防ぐ？

最も分かりやすい設計は、**利用者に自由なファイルパスを渡させないこと**です。

- 例えば `file_id=123` を受け取り、**サーバーが管理する対応表**から実際の保存場所を決めます。
- ファイルパスが必要なら、指定可能な場所を固定し、整理したパスが許可した場所の内側にあるか確かめます。
- ファイルを読むプログラム自体に、**秘密のフォルダーを読む権限を与えない**設計も有効です。
- ファイルを読むときだけでなく、**アップロードや展開、書き換え、削除**でも同じ考え方が必要です。

## ここまでは分からない

**上の短いコードは仕組みを学ぶための判定例で、本番用の安全なファイル読み取り処理ではありません。**

特に、確認した瞬間とファイルを開く瞬間の間に、別の処理がリンクやファイルの場所を変えられる環境では、**「確認したときは安全でも、開くときには別の場所」**という問題が起こり得ます。これは[処理順序の競合](race-condition.md)にも関係します。

「`../` を禁止するだけ」の対処は抜けが生まれやすいので、最初から公開するファイルを絞る設計と、OSの権限設定を組み合わせましょう。
