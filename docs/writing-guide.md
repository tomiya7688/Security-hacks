# Security Hacks の記事の書き方

> **読者は専門用語を覚えに来たわけじゃない。困りごとを解決しに来た。**

## 1. まず「あるある」から始める

記事の最初には、読者が「あ、これ自分のことだ」と思える問いを置きます。

- 「こんなふうに書いていませんか？」
- 「これが起きたら困る、と不安になったことはありませんか？」
- 「〇〇だから安心、と思っていませんか？」
- 「これって、何を確認すればいいんでしょう？」

**無理に不安をあおらないこと。** 本当にありそうな場面を、短く、具体的に書きます。すべての記事で同じ決まり文句を繰り返す必要はありません。

## 2. 名前を教えるより先に、意味を説明する

専門用語を使って専門用語を説明しません。**ふつうの言葉 → 具体例 → 名前** の順で進めます。

### ❌ 伝わりにくい例

> 認可の脆弱性を防ぐには、リソースごとにアクセス制御を実装しよう。

### ✅ このリポジトリでの書き方

> ログインしていても、ほかの人の注文履歴まで見えてしまったら困りますよね。
>
> そこで、画面やデータを開こうとするたびに「この人はこれを見てもいい？」と確認します。
>
> **誰に何を許すかを決めること。これを「認可」といいます。**

名前は隠しません。後から検索したり、公式ドキュメントを読んだりするために必要です。ただし、**最初に名前だけ置いて、読者に調べさせない**ようにします。

## 3. 説明のあとは、できることを1つ増やす

手法の記事には、できるだけ次を入れます。

1. **こんな困りごとはありませんか？** — 読者の状況や疑問
2. **何が起きている？** — 難しい言葉を使わない仕組みの説明
3. **これを〇〇といいます** — 必要になったタイミングで用語を紹介
4. **やってみよう** — 前提条件、環境、実行できるコマンドや設定
5. **どこを見ればいい？** — 結果の読み方、期待どおりの状態
6. **ここまではわからない** — できないこと、よくある失敗、注意点
7. **もっと知りたい人へ** — 公式資料などの一次情報

記事によって順序を少し変えても構いません。**読者が迷わないこと**を優先します。

## 4. 避けたいこと

- 用語の説明を別の専門用語に丸投げする。
- 「対策しましょう」「意識しましょう」だけで終わる。
- よくわからないままコマンドをコピペさせる。
- 1回の確認だけで「これで安全」と言い切る。
- 根拠がないのに「絶対」「100%」と断定する。
- 不安を過剰にあおって読者を置き去りにする。

## 5. 書き終わったら確認する

- [ ] 最初の2〜3行で「誰のどんな困りごとか」がわかる
- [ ] 用語は、その意味をふつうの言葉で説明してから登場する
- [ ] コマンドがあるなら、何をするものか説明している
- [ ] 実行結果の読み方と、判断できないことを書いている
- [ ] 自分で管理する環境や許可された範囲で試せる内容になっている
- [ ] 信頼できる参考資料がある

> **「わかった気がする」より「自分で確かめられた」を増やそう。**
