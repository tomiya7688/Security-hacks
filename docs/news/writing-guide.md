# セキュリティニュースの執筆・更新ガイド（執筆者向け）

> **読者は事件名を集めたいのではありません。「自分に関係するか」「今どうすればいいか」を知りたいのです。**

このページは**ニュースを書いたり更新したりする人のための案内**です。ニュースを読む人は[ニュース一覧](README.md)から記事を探してください。

ニュースは公開が遅れるほど価値が下がります。ただし**速さを優先して誤情報を広めることはしません**。

## 公開の基本ルール：一次情報を確認 → 自己レビュー → すぐマージ

**ニュース記事は、執筆者が自分で内容を点検し、問題がなければ速やかにmainへマージします。** 原則として別の人のレビュー待ちで公開を遅らせません。

1. **一次情報を確認する。** 開発元・被害を公表した当事者・公的機関・脆弱性管理元などの最新の告知を確認する。SNSの投稿だけで確定記事にしない。
2. **記事を書く。** [ニュース記事テンプレート](_TEMPLATE.md)を使い、「何が起きた／誰が対象／何が危ない／何をする／何は不明」を説明する。
3. **自己レビューする。** 下のチェックリストをすべて確認し、問題があれば先に修正する。
4. **チェックを確認する。** Markdown・リンク・差分・リポジトリのCIに失敗がないか調べる。失敗時は修正してから先へ進む。
5. **その日のうちに公開することを基本とする。** 自己レビューと必要なチェックが通れば、PRを**待機させずmainへマージ**し、公開した記事を確認する。

**例外：** 根拠が足りない、大きな矛盾がある、実害を招く対処手順しか提示できない、CIが失敗している、ブランチ保護の要件を満たさない場合は、無理にマージしません。事実が確かになった段階で公開します。

この方針はニュース記事の公開に関するものです。ツールや実行コードの変更など、別途レビューが必要な作業まで無条件に即マージする指示ではありません。

## 記事の構成

### 冒頭のメタ情報

- **発表日：** 情報源が発表した日。事件の発生時刻と混ぜない。
- **内容確認日：** 記事を書いた人が公式情報を最後に照合した日。
- **対象：** 製品、バージョン、OS、配布経路、影響する設定・利用者。
- **情報の性質：** 注意喚起、修正版の発表、被害の確認、調査中の報告など。

### 見出しの順番

1. **「自分に関係ある？」という読者の疑問**から始める。
2. **何が起きた？** — 用語より先に、事実を普通の言葉で。
3. **自分にも関係ある？** — 対象と対象外を区別する。
4. **何が危ない？** — 攻撃可能性と実際に発生した被害を区別する。
5. **今、何をすればいい？** — できれば閲覧・確認のみの安全な手順から。
6. **どこまで分かっている？** — 根拠のある事実、当事者の説明、未確定事項を分ける。
7. **情報源** — 公式発表を先に載せ、二次資料があれば補助として使う。

初出の専門用語は**意味を説明してから「これを○○といいます」と紹介する**。大げさな表現、断定できない推測、別件との根拠のない関連付けを避けます。

## 自己レビュー：マージ前に必ず確認

- [ ] **一次資料を開き直した。** 公開直前に公式ページの更新・訂正を確認した。
- [ ] **誰が対象か正しい。** 製品名、バージョン、OS、配布元、影響する条件を照合した。「全利用者」と誤解させない。
- [ ] **日時が正しい。** 公表日、事故発生日、確認日、タイムゾーンを区別した。
- [ ] **数字の意味が正しい。** 要求額と損失額、凍結額と回収額、推定影響人数と侵入成功件数などを混同していない。
- [ ] **確定と未確定を区別した。** 「攻撃可能」「実証された」「実際に悪用された」「調査中」を分けている。
- [ ] **読者が行動できる。** 対象の調べ方、更新の手順、公式の復旧窓口など具体的な情報がある。
- [ ] **手順が安全。** 読み取り専用の確認を優先し、危険な命令を安易に実行させない。自分以外のシステムの探索・検証を促さない。
- [ ] **出典リンクを確かめた。** 原則として当事者・製品提供元・公的機関の一次情報が少なくとも1件あり、リンク先が該当する主張を裏付けている。
- [ ] **記事内のリンクと体裁が正しい。** Markdownのコードフェンス、相対リンク、機密情報の混入を確認した。
- [ ] **一覧を更新した。** [ニュース一覧](README.md)へ記事を追加し、日付順と一覧の更新日を見直した。
- [ ] **PR差分とCIを確認した。** 意図しない変更や失敗がない。

確認できない項目が重要な事実に関わるなら、**確認できないと明記するか、その主張を記事から外す**。根拠を推測で補いません。

## 公開した後も終わりではない

重大な変更・訂正が出たら、**気づいた時点で同じ自己レビューを行ってすぐ修正をマージ**します。

- 以前の記述が間違っていたら、黙って書き換えるだけにせず記事末尾に**訂正日と訂正内容**を残す。
- 公式発表の影響範囲が変更されたら、**対象製品・バージョン・OS・日時を優先して更新**する。
- 対策状況の表は、**いつの時点の情報か**を明示する。古い表を最新状況と誤解させない。
- 修正が間に合わない重大な誤情報を見つけたら、確証のない部分を先に公開記事から外す。
